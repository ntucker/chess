This is Opening Night, an Expo app for learning chess openings by playing them. Read `GOALS.md` before you design a feature or choose between approaches: it says what the app is for and which platforms it targets.

## Project

- `src/app/` Expo Router screens: every file there is a route and `_layout.tsx` files define navigators, so components, hooks and helpers live outside it.
- The web app is a static export (`web.output: "static"`), deployed to GitHub Pages by `.github/workflows/web.yml`; `app.config.ts` sets the base path from `PAGES_BASE_PATH`. Same-repo pull requests get an unminified preview under `pr-preview/pr-<number>/` (README.md, "Web deploys"). There is no server: don't add API routes.
- The web build pre-renders HTML, so nothing may read the window size or color scheme during the first render. Nor may it read data with `useSuspense`: Data Client fetches in an effect, so the export waits forever. Pre-render the page frame and read data in children of `<BrowserOnly>` (`src/components/BrowserOnly.tsx`). Keep Expo Router's `asyncRoutes` off in `app.json`: a screen whose file loads on its first visit opens blank. A file a page loads late (a lesson, Maia's worker) is gone once enough deploys have replaced the page's build: its loader turns the failure into a `NewVersionError` when the site serves a newer build (`src/files/newVersion.ts`), which the screen shows with a reload (`src/components/NewVersion.tsx`; the root layout's `ErrorBoundary` shows any other error a screen throws). Use `src/theme/useColorScheme.ts`, and lay out with flexbox rather than `useWindowDimensions`. A narrow page (too narrow for the panel beside the board) is decided by one media query in `src/theme/narrow.css` on the web, and only in `src/theme/Narrow.tsx` natively, from the safe-area frame less its insets; no component reads which it is. Its lengths come from `narrowLength`, read in styles built by `narrowStyles`, and anything else from parts named with `useNarrowPart`, each with its native style in `NATIVE_PARTS` (`src/theme/narrow.ts`; `narrow.test.ts` keeps it and the CSS in step); there the board stays at the top and the panel scrolls below it, until the panel reaches its floor and the page scrolls instead. The board's fit to a short screen is the one layout read of the window's height: `useNarrowViewport` (`Narrow.tsx`) natively, a `clamp()` in `src/theme/sideBySide.ts` on the web. The lesson's panel there sets its moves and its idea side by side; the move stepper's middle button opens the scoresheet in their place (`ScoresheetDrawer.tsx`), and the header's gear opens the settings in a sheet (`src/components/Sheet.tsx`). Silk's layout components (`Stack`, `Inline`) set their direction and alignment as inline styles, which outweigh narrow.css: a part that changes those must be a React Native `View`.
- `src/game/` chess rules and game state, built on `chessops`. `game.ts` (the reducer) and `replay.ts` (the rules) are pure functions with no React or React Native imports; `useGame.ts` connects them to React and to the opponent's engine. The game state is only the moves, the shown ply and the opponent's failure; everything else is derived.
- `src/analysis/quality.ts` labels each move (best, good, inaccuracy, mistake, blunder; `book` is reserved for lesson data) by the expected score it gives away, with the thresholds and their sources in one place. `useMoveQualities.ts` labels each move from the final analyses (`PositionAnalysis`) of the positions before and after it, by the engine its caller names (a lesson always Stockfish, free play the bar's engine); only the move the board shows asks for them. `judgeMove`: a move the position before lists is labelled from its own line, so a label never contradicts the list the learner saw; another from the position after's first line, but never better than the list's last move. Labels read only final analyses (`judgeMove` takes a `FinalAnalysis`), so the same game gets the same labels in every mode and visit order (`useLesson.engine.test.tsx` pins it). How a label looks is `src/theme/moveQuality.ts`, which imports nothing so the board's web view can use it too.
- `src/lesson/` lessons, pure functions like `src/game/`: `lesson.ts` is the lesson file format (JSON in `assets/lessons/`, listed and loaded by `src/resources/lesson.ts`); `check.ts` tests every fact a lesson states against the board (the study's judgments only for legality), and `src/resources/lesson.test.ts` runs it on every shipped lesson. The lesson screen's logic is four layers: `select.ts` reads the tree (where a position stands in the guide, and its candidate moves, most played in the opponent's rating band first, with the opponent's rare ones marked and last; past the guide, Stockfish's top moves as rows), `opponent.ts` answers with the guide's move (in a clean Practice run, steering to lines not yet passed: `steering` in `marks.ts`) and hands over to the opponent engine beyond it, `view.ts` gathers the facts about the shown position, and `guidance.ts` alone decides what a mode or switch hides; `drawings.ts` turns guidance into board drawings and the boards a plan, line or trap plays back through (`plan.ts` plays a plan's routes for it and the checker), `board.ts` (`lessonBoard`) is what the board shows, whether a list row is pointed at or a piece dragged or clicked, `screen.ts` is the screen's one reducer, made of `practice.ts` (the mode: Explore, or Practice with whether the run is clean: no non-book move and no take-back; moves that pick the opening are not judged) and `peek.ts` (what the learner points at, the piece a click selects, and an idea playing back), plus whether the candidate list shows its rare rows, and `useLesson.ts` wires a lesson to `useGame` and the learner's progress (its only React). A lesson's switches (auto play, moves on the board, traps) are settings; book moves are labelled `book` inside `useMoveQualities`, never searched; a trap lands at its punishing reply (`LandedTrap` in `view.ts`). The home page opens on the start position for the side the learner plays as (the `side` setting, a lesson's own at its address; until a line picks a lesson, pressing either name bar's disc swaps it), whose candidates are that side's lessons' first moves (`openings.ts`, from `assets/lessons/index.json`, which lists the lines that pick each lesson and their counted line ends). Where lessons share their first moves (1.d4 d5, then 2.c4 for the Slav or 2.Bf4 for the anti-London) the shared moves are listed until a line picks one, and nobody replies there. A line picking a lesson loads it only then, and stepping back to the shared moves picks another. The screen holds the game above the lesson (`useGame` takes a `useReducer(gameReducer, …)` store) so the moves stay while a lesson loads; `src/app/(openings)/_layout.tsx` draws that one page at `/` and at `/lesson/<id>` (its routes draw nothing), and `useOpeningsGame` keeps the address on the lesson picked, so a reload reopens it and Back returns to the start. The page draws a deferred copy of the game (`useDeferredValue`), so it stays on screen while a lesson the game moved to loads (the start loads nothing, so shows at once); the Suspense fallback there sets no tab title, since React renders it uncommitted meanwhile. The lesson's name above the board opens `/openings` (`src/components/OpeningList.tsx`), every lesson's variations as a tree from the index's `variations` (each with the line games most often play into it; `openingList.ts`), pushed on top of the board's page: Back returns to the game as left, and a picked line opens `/lesson/<id>?variation=<id>`, which starts the game there; `useOpeningsGame` also keeps the game each history entry had when the page left it (the layout passes its route's key), so Back or Forward to it resumes it. Its parts are in `src/components/lesson/`; free play against the engine is `src/app/play.tsx`. Tests read shipped lessons and write lines in SAN through `lesson.fixture.ts`.
- `src/components/Page.tsx` every screen's background, header (`Header.tsx`, with a back button for a page on top of another) and scrolling; `src/components/Stage.tsx` the page every board screen shares: header, board column (`BoardColumn`: name bars, evaluation bar, framed board, move stepper and arrow keys for a `useGame` game) and the panel beside it. A screen in a stack stays mounted underneath the next, so its key listeners (`useScreenKeys.ts`) and its game's opponent and label requests (`useGame`'s `active`) wait for `useIsFocused()`.
- `scripts/import-study/` turns lichess studies and Wikibooks pages into a lesson file (`yarn import-study <name>`, sources listed in `studies.ts` in priority order; usage in `index.ts`). A later source only fills what earlier ones leave open; what else a source can say (a committed PGN, the side it was written for, the ply a one-line source names positions from, lines to leave out) is documented on `StudySource` there. `engineCheck.ts` drops book moves and notes Stockfish contradicts; on every lesson its `fillBook` first picks a book move wherever the guide shows the learner moves but recommends none (one a note calls the main line, else Stockfish's best of them, or Stockfish's own move where it overrules them all, keeping theirs as warnings), since the checker refuses a learner position inside the book without one; `engineCheck` picks again where it overrules one of several guide moves, and ends the line where it overruled the guide's only move, or all of them with no move of its own. Notes a guide wrote on a move order the lesson doesn't play go to the position the learner reaches by another, if nothing explains it there (`transpositions.ts`). Each source's share and what was left out are printed. It also rewrites `assets/lessons/index.json` from every lesson file, since one lesson's first moves change which moves pick another of its side. A study chapter set up from a position (FEN) where another chapter's line goes, even a later one's, is joined to that line (`parseStudy`). Build time only: nothing in the app imports it. Each chapter's fixed comment formats are read without AI (`extract.ts` and one file per format), the chapters merge by position (`merge.ts`), popularity comes from the lichess explorer (`popularity.ts`, cached and resumable), and `checkLesson` must pass before the file is written. `convert/` rewrites every comment with Sonnet (Opus retries ideas the checker refuses, note text it refuses as notation, a move a comment marks `?` with no drawn punishment, a note the word limit would cut, and a note that points to the study itself (its chapters, its buttons); a source with `writtenFor` is the opponent's study (tell by whom its comments call "you"), reworded for the learner and booking nothing unless `recommends`) through the Claude Code CLI (`claude -p`), keeping each answer in `answers/<name>.jsonl`; commit it with the lesson file. After transpositions, `explain/` has Fable write one idea note for each book move no note explains (`unexplained.ts`), refusing any its guards or the checker reject (`notes.ts`), and keeps those answers in `answers/<name>-explain.jsonl`; such a note carries `generated: true`, which the checker holds to stricter rules. Never hand-edit a generated note, since the next import rebuilds it from that file; change the guide's notes, the prompt or a guard, and rerun the import. Only an import run on purpose calls the model, never the tests or the site build; `--no-model` rebuilds from the answers file alone. `/dev/review` shows each note beside its study comment. The study's move numbers are often off by one or two: match a named move by its SAN on the line (`line.ts`), never by number alone.
- `src/components/Board.tsx` the board: `@lichess-org/chessground` in an Expo DOM component (`'use dom'`), so it runs in a web view on native. Its props must be JSON; function props become async messages.
- `src/motion/` list motion: wrap the rows in a `MotionList` keyed by what the list shows (the position, say) and each row in a `MotionView` with a stable `id`. Rows glide when they move; those arriving with `layoutDependency` fade in. Other motion is a spring too (`spring.ts`: reuse one from `springs` where it fits; `springMotion` gives a CSS easing), never a duration in milliseconds. Each platform has its own engine (`MotionList.web.tsx`, `MotionList.tsx`); `tsc` keeps their exports alike. On Android, never animate from JavaScript after a commit (the new layout shows for a frame first) or use `exiting` (it leaves ghost rows).
- `src/board/` what the board draws and reports. `drawing.ts` is the drawing vocabulary (`Drawing`: glow, arrow, line, ring, tint, label, ghost, badge, fade, in named tones whose colors are `src/theme/drawingTones.ts`); callers pass `drawings` and the board knows nothing about lessons. `marks.ts` turns drawings into chessground shapes and CSS classes (pure, tested); `pointer.ts` reports `onDrag`, the square a dragged piece is over, which chessground lacks, and says which pointers hover; the board never previews on hover. Changing only `drawings` never resets the position. A previewed move is the board's `preview` position, drawn over the game's by `preview.ts` (pieces slide in, leaving ghosts), so the board under it stays movable; when the game then reaches that position, the board takes it without sliding again. `/dev/drawings` (`src/board/examples.ts`) shows every drawing for screenshots.
- A game's ending (`gameEnding`, `src/game/ending.ts`) is derived, and shown only while the board shows the game's final position (not during an idea's playback). The board acts it out in its web view (`Board.tsx`, `Board.css`); the banner, `EndingCard.tsx`, is React Native because Android's web view can't load the app's fonts. Both run on one timeline, `ACT_TIMES` (`src/board/endingAct.ts`): retime beats there, never in the CSS. Chessground owns a piece's transform, so animate a king in `::before`. Gate animations on `prefers-reduced-motion: no-preference`, with the static style as the end state. `/dev/endings` plays all three endings.
- `src/maia/` the Maia engine, run on the device:
  - lc0's input encoding and move names are in `maia.ts` and `policy.ts`, the network itself in `network.ts`. The networks are assets (`assets/maia/*.bin`, written by `yarn maia`; Metro bundles `.bin` files because of `metro.config.js`), listed in `models.ts`, which must have one for each rating in `ratings.ts`.
  - `engine.ts` plays a move: the rules run on the calling thread, and the network runs off it through `runNetwork.ts` (a react-native-worklets background runtime on native) or `runNetwork.web.ts` (`maia.worker.ts`, a Web Worker).
  - `network.ts` is a worklet file: it may not import anything, and each function must come before the functions that call it (`yarn lint` enforces both).
  - Maia writes castling as the king taking its rook (`e1h1`). The game records every move through `lineMove` in `src/game/replay.ts`, which writes castling as the king's two-square move (`e1g1`).
  - `maia.test.ts` checks the engine against `reference-moves.json`, the moves a separate reference implementation of the network picks in 162 positions for each of the 1100 and 1900 networks and, for the 1900 network, the win, draw and loss chances it gives them, so a failure there means the engine broke, not that the expected move needs updating. The one exception is a position where the two best moves score almost the same, after a change to `scripts/convert-maia.mjs`: the app's weights are 16-bit copies of the originals and can tip a near tie.
  - `scripts/maia-reference.py` writes `reference-moves.json` from lc0's original `.pb.gz` weights, not the app's `.bin` files (setup and usage in its docstring; Python only, never bundled). Rerun it only after changing the models or adding positions or ratings, and review each move that changes.
- `src/stockfish/` Stockfish, which judges positions for the evaluation bar (Maia can instead; the choice is the `evaluationEngine` setting) and can play the opponent:
  - The engine is the `stockfish` npm package's lite single-threaded WebAssembly build, copied into `assets/stockfish/` by `yarn stockfish` (its loader as `.txt`, so Metro ships it as an asset rather than bundling it). It's GPL-3.0: keep it unmodified and separate, talking to it only with UCI text, and never compile or bundle it into the app's own code. Full Stockfish (the `stockfish-full` opponent) is the package's full single-threaded build, 99 MB: too big to commit or ship in the app, `yarn install` copies it into `public/stockfish/` (git-ignored), which the web export serves. It downloads only while it's the opponent, once, into Cache Storage (`full.ts`): the web app from its own site, Android's web view from the live site (`LIVE_FOLDER` in `fullFiles.ts`), since the app can't hand that much to the web view as it does lite's. Its progress is a `Download` record (`src/resources/download.ts`) the opponent picker shows.
  - It always runs in a Web Worker (`worker.ts`): `StockfishHost.web.tsx` starts one in the page; `StockfishHost.tsx` runs one inside a hidden Expo DOM component (`EngineView.tsx`), since Hermes has no WebAssembly. The root layout hands `<StockfishHost />` and `<FullStockfishHost />` to `StockfishWhileNeeded`, which shows full Stockfish's while it's the opponent, and lite's while the evaluation bar or the opponent uses Stockfish, or a screen in front asks for it with `useNeedsStockfish` (`demand.tsx`; a lesson does, since it always labels moves with Stockfish) and for a minute after (`KEEP_MS`). The host is a prop so screens calling the hook never import it and its DOM view.
  - `engine.ts` makes two engines, `liteStockfish` and `fullStockfish` (`createStockfish`), each with its own host and queue. Each searches one position at a time: the newest one watched (`Stockfish.watch`); a newer one, or nobody watching, stops the running search, and a position still watched starts again later from the beginning. Every search starts fresh (`ucinewgame`), ranks three moves (MultiPV) and is limited by nodes only (`APP_SEARCH`, 2,000,000: the most accurate budget measured, about 3 s in Node and 5 to 6 s on a phone; never a time limit, so every device settles on the same lines; full Stockfish's, only the opponent's move, rank one at 1,000,000, `FULL_SEARCH`, about as long). Its depths are a fixed sequence, so a stopped search found the start of what a full one finds. Watchers hear each whole depth as it finishes (`isWholeDepth` in `uci.ts`: the set printed where a search stops mixes depths, repeats the last one under a new number or holds a bound, and is never used), then the deepest as final. Memory: Stockfish's 16 MB hash table (its default), which a full search fills, plus about 200 bytes a position in the store, kept while the app runs (`getAnalysis` never expires). A host attaches each engine it starts with `attach` once it has the files, detaches it when it stops and fails it when it crashes, or goes quiet for `ANSWER_MS` and then doesn't answer `isready`, or answers it `QUIET_ANSWERS` times in a row with nothing else (a lost command); a slow phone's depth of up to a minute is never failed. `restarts.ts` replaces a failed engine after a growing pause; watched positions wait for the next engine, and one two engines failed on is given up. `forwardNeededLines` passes on only the handshake and `isready` answers, `bestmove`, and scored lines from depth 10 (about 30 lines a search cross Android's bridge). `uci.ts` holds the protocol and the score conversion. `engine.test.ts` runs the real engine in Node; `engine.lifecycle.test.ts` scripts engines to test scheduling, takeover, stopping and failing.
- `src/opponent/` who the learner plays against, as one ladder of difficulty (`Opponent`): a Maia rating from 1100 to 1900, which picks Maia's network, or Stockfish above them, playing its best move: lite, then full (`isStockfish`). Screens read the `opponent` setting rather than naming an engine.
- `src/settings/` the learner's settings: one `Settings` object with one reducer (`settings.ts`, pure), held by `SettingsProvider` at the app root and read with `useSettings()` / `useSettingsDispatch()`. A new setting is a new field there, not a new store.
- `src/progress/` the learner's progress in each lesson: the positions Explore showed (`seen`) and the line ends clean Practice runs reached (`passed`), as short position hashes. It is Data Client data, read and saved on the device by `src/resources/progress.ts` (`getProgress`, every lesson's at once, `addMark`, which adds to what is saved at that moment so other tabs' marks stay, and `ProgressSync`, a Manager taking in what another tab saves). `src/lesson/marks.ts` turns it into the candidate rows' marks; only line ends a clean run can reach through the learner's book moves and the opponent's replies played 10%+ of the time count toward a row's `passed` (`cleanRun.ts`, the one walk both the rows and the index's `lineEnds` use). The rows before a lesson is picked take the marks of the openings they lead to (`openingMarks`), whichever lesson is loaded, from the line ends the index lists for each line, so no lesson loads for them. `src/context/storage.ts` is the only code that touches `localStorage`.
- `src/resources/` Reactive Data Client endpoints. Async data goes through Data Client, even with no server: `getMaiaMove` wraps the on-device engine; `fetchOpponentMove` (`opponent.ts`) plays the opponent's move with Maia, or the first line of Stockfish's final analysis, the move the board's arrow shows; `gameOpponent` wraps it as the opponent `useGame` takes. `analysis.ts` keeps one `PositionAnalysis` per engine and position, which only deepens: Stockfish's three best moves from one search (the bar, the best-move arrow, the list past a lesson's guide and the move labels all read it), Maia's evaluation as one line, or a finished game's result. Screens read it with `useAnalysis`, which shows each depth as it arrives through `AnalysisManager` (it watches Stockfish while a screen shows the position, so pass null while the screen isn't in front: a watched position keeps the engine searching); `getAnalysis` answers only with the final one, for what must wait for it. Read the matching `data-client-*` skill before writing, changing or debugging code that loads or changes data. After adding, removing or upgrading `@data-client/*` packages, run `yarn data-client-skills` and commit the skill links in `.agents/skills`.
- UI is built from `@reactive/silk-native` (Silk's React Native renderer), themed in `src/theme/theme.ts`: a theater look, with velvet plum and spotlight gold in dark mode and ivory paper with curtain red in light mode, DM Serif Display for headlines, Instrument Sans for text and DM Mono for notation. Use Silk's components and recipe props first; custom pieces read colors from `useTheme()` rather than hard-coding them (the board's CSS in `Board.css` is the exception, since it runs in a web view). Check new theme colors with Silk's `checkThemeContrast`. Silk isn't on npm yet: it installs from `vendor/*.tgz`, rebuilt with `yarn vendor:silk` from a Silk checkout.
- The logo and every icon in `assets/images/` are drawn by `scripts/make-brand.mjs` (`yarn brand`). Change the script and run it again rather than editing the images.

## Expo has changed: check the docs, not your memory

Expo ships breaking changes every SDK release, so APIs you remember may be renamed, moved or removed. Before writing code that touches an Expo, EAS or React Native API, read the major version of `expo` in `package.json` and fetch the matching docs (`https://docs.expo.dev/versions/v<major>.0.0/`, or https://docs.expo.dev/llms.txt for an index of every page). If the docs can't be reached from your environment, read the installed package's types and README in `node_modules` instead.

## Commands

The package manager is Yarn 4, through Corepack. Yarn holds back package versions published less than a day ago (`npmMinimalAgeGate`), so a brand-new release may not install until the next day.

```bash
npx expo install <package>  # add packages with this, not yarn add: it picks versions that match the Expo SDK
npx expo start              # start the dev server
yarn format                 # format with Prettier
yarn lint                   # lint
yarn typecheck              # typecheck
yarn test                   # unit tests (Jest, jest-expo preset)
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

If `npx expo install` can't reach Expo's servers, run it with `EXPO_OFFLINE=1`, which takes versions from the list bundled with the installed `expo` package.

Run format, lint, typecheck and tests before declaring any task done. Tests sit next to the code they cover (`*.test.ts`); import `describe`, `it` and `expect` from `@jest/globals`, since TypeScript 6 doesn't load global test types.

## Native builds

- Platforms: see `GOALS.md`. No iOS-only code or config, and no library without Android support.
- `android/` (and `ios/`) are generated (Continuous Native Generation) and ignored by git. Configure native behavior in `app.json`, `app.config.ts` and config plugins rather than creating or editing those directories.
- Expo Go only includes its bundled native modules. Once a library with native code is added, running the app on Android needs a development build: `npx expo run:android` locally, or an EAS build.
- `.yarn/patches/expo-*.patch` (applied through `resolutions` in `package.json`) holds a DOM component's props until its page is ready, since on Android an earlier send rejects and a development build shows the error on every launch. `src/components/expoPatch.test.ts` fails when an Expo upgrade drops it, and says what to do.
- EAS isn't set up yet (there is no `eas.json`). When it is needed, run its CLI as `npx eas-cli@latest <command>` rather than a bare `eas`.
- Prefer Expo's own modules over third-party libraries, and check your available skills before adding a dependency.
